Lab 02 - Troubleshooting Network Problems

osi_troubleshooting.md

The OSI Model and Network Troubleshooting

The Open Systems Interconnection (OSI) model divides network communication into seven layers. It gives troubleshooting a structure: examine the lower layers first, then move upward to locate the stage at which communication fails.

Layer 1 - Physical

This layer carries raw bits over Ethernet cables, optical fiber, or wireless links. Check the cable and connectors, link LEDs, whether the network adapter is enabled, and whether a physical connection exists.

ip link
ethtool enp1s0

ip link shows interface state; inspect whether the relevant interface is UP or DOWN. For an Ethernet adapter, ethtool shows physical-link details. Link detected: yes indicates carrier detection.

Layer 2 - Data Link

This layer supports communication within the local segment. Relevant concepts include MAC addresses, Ethernet frames, switches, and ARP. Check the adapter MAC address, neighbor/ARP table, local connectivity, interface state, and the mapping between the local next-hop IP address and its MAC address.

ip link
ip neigh

The first command also displays interface MAC addresses. The second displays neighbor information and helps inspect IPv4 ARP mappings. For a remote destination, ARP normally resolves the local gateway rather than the remote server.

Layer 3 - Network

This layer handles IP addressing and routing between networks. Check the assigned address, subnet prefix, default gateway, routing table, destination reachability, and path.

ip addr
ip route
ping 8.8.8.8
traceroute 8.8.8.8

ip addr displays assigned addresses. ip route displays routes and the default gateway. Ping tests ICMP reachability and round-trip timing. Traceroute probes routers along the path and can help investigate routing problems. Filtering or rate limiting can prevent diagnostic replies without preventing application traffic.

Layer 4 - Transport

TCP and UDP provide transport between applications. Check the protocol, listening socket, connection state, and whether the destination port is reachable from the client.

ss -tuln
ss -ltn '( sport = :80 )'
nc -zv 192.168.1.10 80

The first command displays listening TCP sockets and UDP endpoints. The second checks the exact HTTP port. Netcat tests whether the client can establish a connection to the target port. A listener is not proof of an application returning a healthy response.

Layer 5 - Session

Session functions establish, manage, and end an application's conversation. Check whether a session starts, remains usable, disconnects unexpectedly, or times out. Authentication or session-maintenance problems may also matter.

ss -tan
ss -tan | grep ESTAB

Socket states such as ESTAB, LISTEN, and TIME-WAIT provide transport evidence that can support a session investigation. They do not fully describe an application's session. In TCP/IP systems, session functions are often implemented in the application stack.

Layer 6 - Presentation

Presentation functions concern representation, formatting, encoding, and encryption/decryption. Inspect TLS negotiation, the certificate, hostname, validity dates, and the expected data format.

openssl s_client -connect example.com:443 -servername example.com
openssl s_client -connect google.com:443 -servername google.com

These commands expose handshake and certificate information. Inspect verification errors explicitly; the mere presence of a certificate is not successful authentication. TLS spans functions that do not map perfectly onto a single OSI layer.

Layer 7 - Application

This layer concerns protocols used by applications, including HTTP, HTTPS, DNS, SSH, FTP, SMTP, and IMAP. Check service availability, HTTP responses, name resolution, web-server configuration, service status, and application logs.

curl -I https://example.com
dig example.com
systemctl status nginx
ssh user@server_ip

Each command tests a different application or service stage.

A Step-by-Step Website Investigation

  1. Physical: Is the link available?
  2. Data Link: Are local neighbor and MAC mappings appropriate?
  3. Network: Are the address, gateway, and selected route correct?
  4. Transport: Is the service listening and reachable?
  5. Session: Does the conversation remain established and usable?
  6. Presentation: Are TLS verification and data encoding correct?
  7. Application: Does the service return the expected result?
ip link
ip addr
ip route
ping 8.8.8.8
ss -tuln
openssl s_client -connect example.com:443 -servername example.com
curl -I https://example.com

Start with link state, then addressing/routing, sockets, TLS, and the application response. A failed ping alone does not establish that HTTPS is unavailable.

#!/bin/bash

# Local network allowed to access SSH
LOCAL_NETWORK="192.168.1.0/24"

echo "Configuring firewall..."

# Reset existing UFW rules
sudo ufw --force reset

# Default policies
sudo ufw default deny incoming
sudo ufw default allow outgoing

# Allow SSH only from local network
sudo ufw allow from "$LOCAL_NETWORK" to any port 22 proto tcp

# Allow HTTP from everywhere
sudo ufw allow 80/tcp

# Allow HTTPS from everywhere
sudo ufw allow 443/tcp

# Enable firewall
sudo ufw --force enable

# Save active firewall rules
sudo ufw status numbered > firewall_rules.txt

echo "Firewall configuration completed."
echo "Rules saved to firewall_rules.txt."

1. The Company Network

This is a star topology. Each server and user computer has a link to one switch. The switch has an uplink to the router. The router is the default gateway and the path to the Internet.

Devices:
- Router/default gateway: 192.168.1.1.
- One Layer 2 switch. Frame forwarding does not require a management IP; no management address is specified here.
- Web server: 192.168.1.10, app.local.
- Database server: 192.168.1.11, db.local.
- Cache server: 192.168.1.12, cache.local.
- User computers: the source lists 192.168.1.100-110 for ten computers.
- Subnet: 192.168.1.0/24.

3. What Happens if the Switch Fails?

The switch is the only Layer 2 path between the hosts. User computers lose access to the web, database, and cache servers. The website becomes inaccessible even if nginx is still running on the web server.

The three servers also lose communication with each other. The web application cannot reach db.local or cache.local. All hosts lose their path to the router, so the default gateway is unreachable and Internet access from this subnet stops.

IP addresses do not change merely because the switch fails. The router can still be powered on, but LAN hosts cannot send frames to it through the failed switch.

Recovery means repairing or replacing the switch, or moving links to a spare. DNS and host-firewall changes do not repair the failed physical switching path. A properly designed redundant switching arrangement can reduce this single point of failure; avoid adding loops without an appropriate redundancy design.

4. What a router is

A router forwards IP packets between networks. It examines the destination address, selects an appropriate matching route, and sends the packet toward the next hop through the chosen interface. The company gateway at 192.168.1.1 routes traffic from 192.168.1.0/24 to other networks. Hosts commonly use a default route for destinations without a more specific route.

Editorial clarification: hosts deliver local-subnet traffic directly through the local Layer 2 network; it does not normally pass through the router. NAT, when configured, is distinct from routing. The claim in the supplied answer that hosts never need specific remote routes is too broad.

tcp_vs_udp.md

TCP versus UDP

1. Main Differences

  1. Connection: TCP normally establishes a connection through SYN, SYN-ACK, and ACK, and ends it with FIN or RST. UDP sends datagrams without this transport handshake.
  2. Reliability: TCP retransmits missing data and delivers an ordered byte stream. UDP does not itself retransmit or reorder data; an application can implement additional recovery.
  3. Flow and congestion control: TCP regulates transmission using receiver flow control and congestion control. UDP itself does not provide equivalent mechanisms; the application protocol must choose appropriate behavior.
  4. Headers and overhead: The basic TCP header is 20 bytes plus options; the UDP header is 8 bytes. Less overhead does not make every UDP application faster.
  5. Application interface: TCP is a byte stream without preserved message boundaries. UDP preserves datagram boundaries.
  6. Failure: A disappeared TCP peer may eventually cause timeout or reset. With UDP, the application may see missing replies and needs its own detection or timeout logic.

2. Suitable Transports

#!/bin/bash
set -e
cd "$(dirname "$0")"
mkdir -p certs
openssl req -x509 -newkey rsa:2048 -nodes \
    -keyout certs/myapp.key -out certs/myapp.crt -days 365 \
    -subj "/C=IR/ST=Tehran/L=Tehran/O=MyCompany/CN=myapp.local"
chmod 600 certs/myapp.key
{
    date -Is
    echo 'openssl x509 -in certs/myapp.crt -text -noout'
    openssl x509 -in certs/myapp.crt -text -noout
    echo 'openssl rsa -in certs/myapp.key -check -noout'
    openssl rsa -in certs/myapp.key -check -noout
    echo 'The certificate is for myapp.local and is valid for 365 days.'
    echo 'Subject and Issuer are identical because the certificate is self-signed.'

SSL and TLS

SSL is obsolete and has been superseded by TLS. HTTPS carries HTTP over TLS.

Self-Signed and CA-Signed Certificates

A self-signed certificate is signed using its own corresponding key and is suitable for a local test. A browser does not trust it by default. A CA-signed certificate chains to a trusted authority and is generally more appropriate for a public website. Both can support encryption; the important difference is trust in the server identity.

Five TLS Practices

  1. Disable obsolete SSL/TLS versions and use supported TLS 1.2 or 1.3.
  2. Check the hostname, certificate chain, and expiration date.
  3. Restrict access to the private key to the service that needs it.
  4. Renew the certificate before expiration.
  5. Use maintained, strong cipher configurations.

HTTP and HTTPS Security

Ordinary HTTP does not encrypt data, allowing it to be read or changed along the path. TLS encrypts data, authenticates the server through certificate verification, and detects tampering. HTTPS does not replace fixing vulnerabilities in the application.

Running the Lab Server

From the corresponding lab directory, run bash generate_ssl.sh and then python3 https_server.py. In another terminal: curl -k https://localhost:8443 Stop the server with Ctrl+C. Only the public directory is served so the private-key file cannot be downloaded through HTTP.

The original hint uses ssl.wrap_socket, which was removed in Python 3.12. The supplied Python 3.14 server uses SSLContext.wrap_socket. Source: https://docs.python.org/3.12/whatsnew/3.12.html#ssl

File Transfer Comparison

MethodAdvantageLimitationUse case
FTP, usually control port 21Legacy tool supportBasic FTP does not encrypt credentials or dataLegacy service or isolated lab
SFTP over SSH, usually port 22Secure transfer and interactive file managementRequires an SSH serviceSecure uploads and downloads
SCP over SSH, usually port 22Copy with one commandLess suited to interactive directory managementQuick file and directory copies

FTP and SFTP are different protocols. SFTP uses SSH. In current OpenSSH versions, scp uses SFTP by default.

ftp 127.0.0.1
sftp mohammad@192.0.2.10
scp report.txt mohammad@192.0.2.10:/home/student/

SFTP or scp is more appropriate on a public network because the connection is encrypted. Source: https://man.openbsd.org/scp

cdn_explanation.md

CDN

A CDN, or Content Delivery Network, uses servers at distributed locations. It can store images, CSS, and JavaScript closer to users. Serving content from a nearby edge can shorten the path and reduce latency. Cache hits can also reduce the load on the origin.

The origin server is the primary content source. An edge server can be closer to the user and can serve a cached copy. On a cache miss, it may fetch content from the origin.

Example from the hint:

curl -I https://cdn.jsdelivr.net/npm/jquery@3.6.0/dist/jquery.min.js

Recorded output is in cdn_headers_test.txt. Headers to inspect include X-Cache, CF-Cache-Status, and X-Served-By. In relevant cache-status headers, HIT indicates a cache hit and MISS indicates a miss for that request. CDNs expose different headers; a missing particular header does not prove the absence of a CDN.

#!/bin/bash
cd "$(dirname "$0")" || exit 1
{
    date -Is
    echo 'Domain | IPv4 | TTL (seconds) | DNS server | Query time (ms)'
    for domain in google.com github.com stackoverflow.com linkedin.com; do
        response=$(dig +time=3 +tries=1 "$domain" A)
        server=$(echo "$response" | awk '/^;; SERVER:/{print $3}')
        query_time=$(echo "$response" | awk '/Query time:/{print $4}')
        if echo "$response" | awk '$4=="A"{print $5}' | grep -q .; then
            echo "$response" | awk -v domain="$domain" -v server="$server" -v ms="$query_time" \
                '$4=="A"{print domain " | " $5 " | " $2 " | " server " | " ms}'
        else
            echo "$domain | no A answer | - | $server | $query_time"
            echo "$response"
        fi
    done
    echo 'IP addresses and TTLs were extracted from ANSWER SECTION; the resolver was extracted from SERVER.'
    echo 'Query time measures the DNS exchange, not the time to open a website.'
    echo '127.0.0.53 in SERVER means the query was answered through the local stub resolver.'
} > dns_analysis_report.txt 2>&1

ssh_tunneling_guide.md

Local Port Forwarding

ssh -L 8088:localhost:80 mohammad@192.0.2.10

Client port 8088 forwards to port 80 as seen from the SSH server. Use case: access a web service that listens only on server localhost. After creating the tunnel, request http://localhost:8088 on the client.

Remote Port Forwarding

ssh -R 9000:localhost:3000 mohammad@192.0.2.10

Server port 9000 forwards to port 3000 as seen from the SSH client. Use case: let the server access a development application on a laptop. By default, this remote listener is bound to server loopback.

Dynamic Port Forwarding

ssh -D 1080 mohammad@192.0.2.10
curl --socks5-hostname localhost:1080 https://example.com

A SOCKS proxy is created on the client; the application chooses each destination. Use case: test access through the SSH server network path.

Add -N when no remote command is needed. The recorded local test used HTTP destination port 8080, local listener 8088, remote listener 9000, and SOCKS listener 1080. Results are in ssh_lab_test.txt. The test client and sshd ran as separate processes on the same machine.

#!/bin/bash
cd "$(dirname "$0")" || exit 1
source_path=${1:-/var/log}
pattern='sshd|systemd-networkd|NetworkManager|dhcp|systemd-resolved|nginx|vsftpd|UFW|firewall|TCP|UDP'
if [ -f "$source_path" ]; then
    files="$source_path"
else
    files=$(find "$source_path" -type f \( -name '*.log' -o -name syslog -o -name kern.log -o -name auth.log \) 2>/dev/null)
fi
: > network_events.txt
{
    date -Is
    echo 'Network-related readable text log files:'
    for file in $files; do
        if [ ! -r "$file" ]; then
            echo "Cannot read: $file"
        elif grep -qiE "$pattern" "$file"; then
            echo "$file"
            grep -hiE "$pattern" "$file" >> network_events.txt
        elif [[ "$file" == *nginx* || "$file" == *vsftpd* ]]; then
            echo "$file"
            cat "$file" >> network_events.txt
        fi
    done
    echo 'Latest 10 matching events with ISO timestamps:'
    grep -E '^[0-9]{4}-[0-9]{2}-[0-9]{2}T' network_events.txt | sort | tail -10
    echo 'Other timestamp formats are included in counts but are not ordered in this list.'
    echo 'IPv4 occurrence counts:'
    grep -Eo '([0-9]{1,3}\.){3}[0-9]{1,3}' network_events.txt | sort | uniq -c | sort -nr
    echo 'IPs with at least 3 failed login events:'
    grep -iE 'Failed password|Failed publickey|Invalid user|authentication failure' network_events.txt |
        grep -Eo '([0-9]{1,3}\.){3}[0-9]{1,3}' | sort | uniq -c | awk '$1>=3' | sort -nr
    echo 'Repeated failures need investigation; they are not proof of an attack.'
} > log_analysis_report.txt 2>&1

network_monitor.sh
#!/bin/bash
cd "$(dirname "$0")" || exit 1
if [ "$(id -u)" -ne 0 ]; then
    echo 'Run with sudo: sudo bash network_monitor.sh'
    exit 1
fi
if ! command -v tshark > /dev/null; then
    echo 'tshark is required for measuring traffic per IP.'
    exit 1
fi
interface=$(ip route show default | awk 'NR==1{print $5}')
if [ -z "$interface" ]; then
    echo 'No default network interface found.'
    exit 1
fi
tshark -i "$interface" -l -f ip -T fields \
    -e ip.src -e ip.dst -e ip.len > traffic.tsv 2> capture_status.txt &
capture=$!
trap 'kill "$capture" 2>/dev/null' EXIT
trap 'exit 0' INT TERM
sleep 1
while true; do
    if ! kill -0 "$capture" 2>/dev/null; then
        cat capture_status.txt
        exit 1
    fi
    lines_before=$(wc -l < traffic.tsv)
    rx1=$(awk -v dev="$interface:" '$1==dev{print $2}' /proc/net/dev)
    tx1=$(awk -v dev="$interface:" '$1==dev{print $10}' /proc/net/dev)
    start=$(date +%s)
    sleep 5
    lines_after=$(wc -l < traffic.tsv)
    seconds=$(( $(date +%s) - start ))
    rx2=$(awk -v dev="$interface:" '$1==dev{print $2}' /proc/net/dev)
    tx2=$(awk -v dev="$interface:" '$1==dev{print $10}' /proc/net/dev)
    {
        date -Is
        ip -s link show "$interface"
        echo "Sample interval: $seconds seconds"
        echo "Download: $(( (rx2-rx1)/seconds )) bytes/s"
        echo "Upload: $(( (tx2-tx1)/seconds )) bytes/s"
        echo "Active TCP connections: $(ss -Htn state established | wc -l)"
        echo 'Top 5 IPv4 addresses by sent + received packet bytes:'
        tail -n "+$((lines_before+1))" traffic.tsv | head -n "$((lines_after-lines_before))" |
            awk 'NF==3 {bytes[$1]+=$3; if($2!=$1) bytes[$2]+=$3}
                 END {for(ip in bytes) print bytes[ip], ip}' | sort -nr | head -5
        echo
    } | tee -a monitoring_log.txt
done
